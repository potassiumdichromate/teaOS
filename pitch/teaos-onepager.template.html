The operating system for high-stakes assessment.

Every high-stakes assessment on earth runs on improvised software — a question bank from one vendor, delivery from another, proctoring from a third. teaOS is the layer underneath all of it: AI validates content inside hardware-attested enclaves, every artifact is encrypted onto decentralized storage, the key that unlocks an assessment is released by a public cryptographic schedule no administrator can move, and autonomous agents watch the whole lifecycle without ever holding authority themselves. Governments, universities, enterprise hiring teams, certification bodies, and recruitment platforms all run on the same kernel, because integrity here is a property of the system, not a promise from the institution.

The problem

Assessment never got an operating system.

Every other domain that handles something valuable eventually grew a layer that handles it properly. Payments got settlement rails. Healthcare got records systems. Assessment got a spreadsheet, a mail merge, and a lot of trust.

What institutions run today isn't a platform — it's an assembly. A question bank in one vendor's database. Delivery through a second vendor's portal. Proctoring bolted on from a third. Results computed somewhere else entirely. Every handoff between them is a place where integrity has to be assumed, because nothing in the stack can prove it.

So the failures are structural, not moral. A paper leaks because somebody legitimately held it. A result is disputed because the only evidence lives on the accused institution's own servers. A candidate who suspects something has no way to check anything at all. These aren't separate problems — they're the same missing layer, showing up in four places.

You cannot patch your way to trustworthiness on top of an architecture that requires trust at every seam. That layer has to exist underneath, or it doesn't exist.

Why now

The primitives this needs didn't exist five years ago.

Leaked papers and disputed results are as old as assessment itself. What's new is that the infrastructure to close the gap properly has shipped, in production, only in the last few years — this isn't a research bet, it's an assembly job that finally became possible.

Confidential compute

Shipped, not theorized

Intel TDX enclaves with attestable inference are a selectable API tier today, not a research paper — we verified this live against a production provider before depending on it.

Threshold cryptography

Left the whitepaper

drand's threshold beacon has run in production for years across independent operators. Timelock encryption on top of it is a maintained library, not an unproven primitive.

AI review

Good enough to gate, not just assist

Duplicate detection, bias, and difficulty prediction are reliable enough now to gate acceptance into a question bank — advisory input to deterministic rules, not a human's only line of defense.

Assessment volume

Compounding faster than trust

Hiring, certification, and government testing keep moving online while the underlying leak rate hasn't improved — the failure mode this exists to close is getting more frequent, not less.

The system model

A kernel, a set of primitives, and everything else in userland.

teaOS is structured the way operating systems are structured, because the problem has the same shape: many different workloads, sharing one substrate, that must not be able to interfere with each other or with the guarantees underneath them.

Kernel interface

Seven primitives. Everything else is composition.

These are the operations the kernel exposes. An assessment — any assessment — is a sequence of calls into them. Each one carries a guarantee the caller cannot weaken, no matter what privileges the caller holds.

seal(payload, until_block)

Encrypts a payload and places its key beyond retrieval until a specific block height. The caller receives a reference, never the key.

Guarantee — no caller, at any privilege level, can produce the key before the height is reached.
schedule(window)

Binds a human schedule to block heights, recording the derivation so the mapping from "09:00 Tuesday" to a specific block is itself auditable.

Guarantee — the release condition is not a clock, so it cannot be moved by touching a server.
derive(session, seed)

Deterministically renders one candidate's view of a paper — question order, option order — from a stored seed, reproducibly, forever.

Guarantee — reconstructible years later from a few bytes, without storing a personalized copy.
commit(submission)

Publishes a private, non-repudiable commitment to a submission. Reveals neither identity nor content; the registry itself refuses a second write for the same session, permanently.

Guarantee — a submission cannot be altered after the fact, or denied to have happened.
attest(inference)

Runs a model against protected content inside a hardware enclave and returns the result plus proof of where it executed.

Guarantee — content is never readable by the model host, the vendor, or us.
anchor(hash)

Writes an immutable record of what existed and when, to infrastructure outside the institution's control and outside ours.

Guarantee — the record survives us, and cannot be rewritten by anyone who compromises us.
verify(claim)

Re-derives any assertion the system has made, from original sources, without consulting the application database.

Guarantee — anyone can run it, including people we have no relationship with.

Process isolation

Four services that cannot become each other.

The system is decomposed along privilege boundaries, not for scaling convenience. The process serving your web session and the process holding decryption keys are separated by design, and there is no configuration that merges them.

Service 01

Application API

Node · Express · PostgreSQL · Redis

Identity, scheduling, blueprints, sessions, orchestration. The surface the internet talks to, and deliberately the least privileged component in the system.

  • canQueue work, read metadata, write audit records
  • cannotDecrypt a question or a paper
  • cannotReach a paper key, even with full database access
Service 02

Crypto workers

Isolated queue consumers · BullMQ

Where encryption happens. Pulls jobs from Redis, performs envelope encryption, writes to storage, signs chain transactions. Holds the question-bank master key.

  • canEncrypt, decrypt, assemble, anchor
  • cannotBe reached directly over HTTP
  • cannotRetain a paper key past assembly
Service 03

Timelock service

TypeScript · drand / tlock

Sits behind the kernel's seal primitive so the decentralized network underneath it is swappable without touching anything above — proved when we actually swapped it: first against Miden's protocol on its devnet, now against drand's production threshold network, with no change to the interface the rest of the system calls.

  • canSeal keys, release them at a target round
  • cannotRelease a sealed key before its target round
Service 04

Chain registries

Solidity · 0G Chain

Five append-only contracts — questions, papers, submissions, results, audit log. They store hashes and block numbers, and nothing else.

  • canProve what existed, and when
  • cannotHold content, identity, or scores
  • cannotBe rewritten, including by us

The first working implementation, against Miden's client, needed its own isolated thread — its transaction prover loses its Send bound at an API boundary, so it couldn't share an async server's request threads. Swapping to drand/tlock removed that constraint entirely: sealing is a pure encryption call against a public beacon, so it now runs as a direct library call in the same process as everything else. The interface above it — seal, schedule — never changed; only the machinery behind it got simpler.

Key management

Two keys, with deliberately different lifetimes.

Most systems claiming encryption have one key that opens everything, kept somewhere convenient. The design work here is in the second key — the one that exists for a few seconds and then stops being ours.

Assembly runs in a fixed order, and the order is the point. Workers decrypt selected questions individually, compose the paper in memory, generate a fresh content key, encrypt under it, upload the ciphertext, anchor its hash — and only then seal the key and drop it.

Between assembly and assessment start, the paper key exists in exactly one place: inside a sealed note the network refuses to open. Not in a database. Not in a vault we control. If our entire infrastructure were seized during that window, the paper would still be unreadable.

The scheduler

Release as a protocol event, not an application decision.

A scheduled release in ordinary software is a timestamp column and a background job — anyone with write access can move the date and nobody outside would know. The release condition needed to live somewhere no operator could reach.

The paper's content key is encrypted against a specific point in a public, ongoing schedule run by a decentralized network — nobody can produce the material needed to decrypt it before that point arrives, because doing so requires a threshold of independent parties to cooperate, not one operator's permission. Reaching the target point is what releases the key; nothing in our stack decides to release it.

We proved this end to end against Miden's protocol first — sealing the key into a timelocked note whose script refuses release until a target block height, verified with a real transaction executing on Miden's devnet. Production runs on drand/tlock instead: the same guarantee, built on a threshold-signature network that has run in production for years rather than a pre-1.0 client. The mechanism changed after Miden's own public testnet spent two days rejecting its newest published SDK version — we switched rather than keep waiting on someone else's rollout. The guarantee — release enforced by a decentralized network, with no admin override anywhere in the path — did not change.

Half one

The encrypted paper

Sits in decentralized storage. Anyone can download it. Without the key it's a wall of ciphertext — AES-256-GCM, no shortcuts.

Half two

The key, timelocked

Sealed to a target point in a decentralized network's public schedule, which refuses to release it early. Not a permission check. A protocol rule.

System daemons

AI agents that monitor the assessment — and are monitored themselves.

A 40,000-candidate assessment produces more behavioural signal in three hours than a human team could review in a month. Automating that is obvious. What isn't obvious — and what every proctoring vendor quietly skips — is answering who audits the automation.

Most AI proctoring is a black box that flags a candidate, produces a confidence score, and ends a career. The candidate cannot see the evidence, cannot contest the model, and cannot establish that the same behaviour wouldn't have been flagged in someone else. That's not monitoring, it's an unappealable verdict from software.

teaOS treats agents as system daemons subject to the same kernel guarantees as everything else. They run inside enclaves, so they never see raw candidate data in the clear. Every judgement they make is anchored with the evidence that produced it. And critically, no agent holds authority — they escalate to humans with a signed evidence bundle, and the consequence is always a human decision that is itself recorded.

Verification

Six independent checks, no login required.

A candidate enters an application number and date of birth. The system doesn't read a stored "verified" flag — it re-derives every claim from source and reports each separately, so a partial failure is visible instead of hidden behind one green tick.

  • 01Answer hash matches The answers on record hash to the value committed at submission time.
  • 02Submission hash matches The submission commitment matches what was anchored, byte for byte.
  • 03Official result hash matches The published score re-derives to the hash anchored in ResultRegistry.
  • 04On-chain commitment is consistent The registry contract itself is read directly — not our database — and its own write-once guard is what made a second submission impossible in the first place.
  • 05Storage Merkle proof verifies The stored blob proves membership under the root that was anchored.
  • 06Chain transaction is valid and final The anchoring transaction exists on chain at the stated block.

None of these consult our database. Each goes to the original source and recomputes. A journalist, a court, or a competing vendor can run the same checks against public infrastructure and get the same answer without our cooperation — which is the only definition of verification that means anything.

What the kernel required, and what met it.

We didn't start from a shortlist of chains. Each requirement came out of the kernel design, and only then did we go looking for something that satisfied it.

A release condition no operator can override

Everything else is downstream of this. If any human can move the release time, the whole guarantee collapses. It had to be enforced by a decentralized network, not by application logic.

Kernel guarantees

The failures we designed against.

Security systems rarely fail loudly. They fail by reporting success while doing nothing. Three of these were found by running the system rather than reasoning about it, which is the main reason we trust the rest of it.

Failure mode

Silent success

An unimplemented endpoint returned an error message with a success status code. The caller's check passed, the error body parsed as a valid result, and a paper was marked ready with no timelock attached to it at all.

NowEvery kernel response is validated against a strict schema regardless of status code. A well-formed lie fails as loudly as a crash.
Failure mode

The privileged exception

The usual way a system like this rots is an emergency override added under pressure — "just for the admin, just this once" — which then becomes the thing an attacker targets.

NowOne code path gates assessment start for every role. There is no branch on privilege, so there is nowhere to add an exception without removing the check entirely.
Failure mode

Orphaned key material

The bridge originally provisioned a fresh account on every restart, which would have stranded sealed notes behind an identity the service no longer possessed.

NowAccounts persist across restarts and are verified present before reuse, with a fresh pair provisioned only if that check fails.
Failure mode

Retries corrupting state

A queued job failing partway through an external call would re-enter and hit a state guard written for the first attempt, reporting a confusing conflict instead of genuinely retrying.

NowState machines accept their own in-progress states as valid re-entry points, so a retry is a retry rather than a spurious error.

Workloads

Who runs on it.

Five segments, one shared problem: they all make consequential decisions from test scores, and none of them can currently prove the test wasn't compromised.

Enterprise & MNC hiring

10K – 500K candidates / year

Campus recruitment, lateral hiring assessments, internal promotion tests, global certification programs run across dozens of countries.

A leaked question bank quietly destroys the validity of every hire made from it — and there's no defensible record when a rejected candidate disputes the outcome.

Universities & colleges

5K – 200K candidates / year

Entrance tests, semester assessments, online degree evaluation, and remote programs across multiple campuses.

Internal leaks are common and rarely reported. Retakes are expensive, and accreditation bodies increasingly ask for an audit trail nobody can produce.

Government & public boards

100K – 5M candidates / year

National and regional competitive assessments, civil service recruitment, public sector selection at population scale.

A single leak means mass cancellation, litigation, and political consequence. This is where the cost of failure is highest and scrutiny is total.

Certification bodies

20K – 1M candidates / year

Professional licensing, IT and cloud certifications, skills credentialing, continuing education requirements.

Proxy testing and credential fraud attack the one thing a certification body actually sells — the belief that the certificate means something.

Recruitment & hiring platforms

Embedded in platforms serving 50K – 2M candidates / year

ATS vendors and assessment marketplaces that want to sell verifiable integrity to their own customers without becoming a cryptography company themselves — one API, resold under their own brand.

Every platform in this category currently sells trust it can't back up. A flagged candidate has no more recourse with the platform than with the employer who used it.

We're starting with enterprise recruitment and private universities: shorter sales cycles, real budgets, and the same integrity problem at a scale where we can prove the system before approaching public boards.

Not the assessment. Not the results. One moment: when a paper becomes readable. Everything on either side of that is ordinary engineering.

Six years across major chains and four in decentralized AI infrastructure is mostly an education in which guarantees are real and which are marketing. That's the judgement teaOS needed — the discipline to use cryptography for exactly one thing that genuinely requires it, and conventional engineering everywhere else.

It's also why the hard part was tractable. Sealing a key to a block height means working against pre-1.0 tooling with no reference implementation, which is uncomfortable unless you've spent years at that layer already.

The easy version of this is a model that flags suspicious candidates. Anyone can ship that in a week. The version that should exist is one whose reasoning a nineteen-year-old can read, challenge, and win against when it's wrong. If software gets to influence whether someone gets a job, it doesn't get to hide how it decided.

Building agent systems across the full ML stack teaches you that accuracy is the easy metric. The hard one is whether a system's judgement survives being questioned — which is the entire design constraint on teaOS's monitoring layer.

That's why every daemon emits evidence a human can inspect rather than a score, and why none of them hold authority. It's a harder system to build, and the only kind that belongs anywhere near someone's career.

Between us, the two halves of the claim are covered: infrastructure that provably holds, and AI restrained enough to be trusted near a consequential decision. The system described on this page is deployed, not planned — which is the only version of this pitch we were willing to make.

Where this goes

Integrity shouldn't require trust.

Every year, hundreds of millions of people sit an assessment that decides what the rest of their life looks like — and are asked to believe, on faith, that nobody opened the paper early. When that faith breaks, it doesn't just cost a result. It costs a year, a rank, a job, sometimes a career.

Assessment is one of the last consequential systems still running without a foundation underneath them. teaOS is that foundation: a kernel where the guarantee is enforced by mathematics that answers to no one, and where any candidate, on any phone, can check it for themselves in ten seconds.

We're not asking institutions to be more trustworthy. We're making trustworthiness something they no longer have to be taken at their word for.
