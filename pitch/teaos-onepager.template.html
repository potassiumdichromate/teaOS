The problem

Every paper leak ends the same way.

An investigation. A committee. A promise it won't happen again. Then the same system gets rebuilt, exactly as it was.

The reason isn't that people running exams are careless. It's structural. In every exam system operating today, some human being holds the question paper before the exam starts — a database administrator, a printing vendor, a regional officer, someone with production access at 2am. Security is a rule asking them not to look.

A rule has no enforcement layer. And when something does go wrong, the audit logs that would prove it sit on servers owned by the same institution being investigated.

Every exam system in the world currently asks candidates to trust an administrator. teaOS removes the administrator from the trust equation — not with policy, with cryptography.

What we're building

A complete operating system for examinations.

Not a proctoring plugin. Not a question bank with a login screen. The whole stack — authoring through verification — with a cryptographic guarantee under every layer.

Institutions today stitch together four or five vendors: one for the question bank, one for delivery, one for proctoring, one for results. Every seam between them is a place where trust has to be assumed and integrity can't be proven. teaOS collapses that into one system where each stage hands the next a verifiable artifact instead of a promise.

How it works

Five stages, each one provable.

  1. 01

    Authors submit questions

    Each question goes straight into a confidential AI review — duplicate detection against the existing bank, difficulty prediction, bias and grammar checks, cognitive-level classification. It runs inside a hardware enclave, so the question text never sits readable on anyone's server. Pass, and it's encrypted and anchored. Fail, and the author gets specific feedback.

    0G Compute · Intel TDXAES-256-GCM0G Storage
  2. 02

    The institution designs a blueprint, not a paper

    Administrators set the shape — subject weightage, topic spread, difficulty mix, marks, negative marking. They never pick individual questions. The system assembles the paper deterministically from the approved bank, and no human sees the assembled result.

    Deterministic selectionPer-candidate seedPaperRegistry
  3. 03

    The paper is sealed until exam time

    The assembled paper is encrypted with a fresh key. That key is wrapped into a Miden P2IDE note with a timelock height set to exam start. Until that block arrives the note cannot be consumed — enforced by the note script running in Miden's VM, not by our application code.

    Miden P2IDE notetimelock_height = exam start
  4. 04

    Candidates sit it, submissions commit privately

    Question and option order are shuffled per candidate from their own seed — same questions, same difficulty, different arrangement. Answers autosave encrypted. On submit, a private Miden note commits the submission; its nullifier makes silent resubmission impossible without revealing what was answered.

    Private notesNullifier-basedSubmissionRegistry
  5. 05

    Results anyone can verify — no login

    Evaluation and ranking run in an access-controlled service and anchor the result hash on chain. A candidate enters their application ID and date of birth on a public page, and the system re-derives everything from scratch: answer hash, submission hash, official result hash, note status, storage proof, chain transaction.

    ResultRegistryRank generationPublic portal

The core guarantee

Two halves. Neither one is enough.

This is the single idea the whole product rests on. The paper and the key that opens it live in different places, under different rules, controlled by nobody in particular.

Half one

The encrypted paper

Sits in 0G Storage. Anyone can download it. Without the key it's a wall of ciphertext — AES-256-GCM, no shortcuts.

Half two

The key, timelocked

Wrapped inside a Miden note whose script refuses to release it before the exam-start block. Not a permission check. A protocol rule.

Sealed · block height not reached
timelock_height = exam start  ·  reclaim_height = window close
encrypted paper + released key = readable, and only now

We tested this the only way that counts — by trying to break in from every direction, using real accounts on a real deployment.

  • AdmindeniedHighest-privilege account. No override key exists to give them.
  • Exam centredeniedAuthorization endpoint returns unauthorized, with the reason.
  • CandidatedeniedExam start refused; paper status is not READY.
  • UsdeniedSame code path. We built it and we can't open it either.
There is no backend override. Not because we chose not to build one — because the architecture has nowhere to put it.

Design decisions

Why each piece is there.

Why blockchain at all

Because a database is owned by whoever is being investigated.

This is the honest answer, and it's the only one that matters. Exam boards already keep meticulous logs. The problem is that when a leak is alleged, those logs sit on infrastructure controlled by the institution under scrutiny — and no candidate, court, or journalist can independently confirm they weren't edited after the fact.

Anchoring content hashes to a public chain isn't decentralization as ideology. It buys one specific property: the record exists outside the institution's reach and can't be rewritten later — by them, by us, or by anyone who compromises either of us.

Why Miden

Because the timelock has to be enforced by physics, not by a manager.

Most "scheduled release" systems are a database column and a cron job. Anyone with write access can change the date. Miden gives us something categorically different: P2IDE notes carry a timelock_height enforced by the note script inside Miden's VM. There is no admin to bribe, because there is no admin in the path.

Miden also does client-side proving, so key material never has to exist on a server that can be subpoenaed or breached. And its private notes let submissions commit on-chain without publishing who answered what — a nullifier prevents resubmission while the content stays confidential. For an exam system, that combination is unusually exact.

Why 0G

Because question validation needs AI that nobody gets to read over.

Checking a question for duplicates, bias, and difficulty needs a real model. But sending an unreleased exam question to a normal inference API means handing the paper to a third-party vendor. 0G Compute runs inference inside Intel TDX hardware enclaves with attestation, so we can prove where it executed and that the content stayed sealed.

0G Storage gives us content-addressed encrypted blobs with Merkle proofs — a stored paper can be proven byte-identical to what was anchored. And 0G Chain is an EVM L1 cheap enough to anchor at per-question granularity instead of batching daily, which is what makes the audit trail fine-grained enough to actually be useful.

Why not just build it centrally

Because we'd be asking for the same trust everyone else already asked for.

A centralized teaOS would be faster to build and easier to sell. It would also be one insider away from the exact failure it claims to prevent — and there'd be no way for a candidate to tell the difference between a system that works and one that quietly doesn't.

What comes next

Autonomous agents that watch the exam, and can be audited themselves.

The next layer of teaOS is agentic. Exams generate enormous amounts of signal that no human team can watch in real time — and the moment you automate that watching, you create a new trust problem: who audits the watcher?

Our answer is that agents get the same treatment as everyone else in this system. They run inside 0G Compute enclaves, so they never see raw candidate data in the clear. And every judgement they make — every flag, every escalation, every intervention — is anchored on chain with the evidence that triggered it. An agent's decisions become exactly as reviewable as a human invigilator's, except they don't get tired at hour four.

Agent 01

Live invigilation

Watches session telemetry across every centre simultaneously — focus loss, timing irregularities, input patterns — and produces a signed evidence bundle instead of an unexplained accusation.

Runs in TEE · decisions anchored · human review required before action
Agent 02

Collusion detection

Statistical analysis across centres and cohorts to surface coordinated answer patterns that are invisible when each session is examined alone.

Cross-centre correlation · privacy-preserving aggregates
Agent 03

Question bank health

Continuously audits the bank for over-exposure, difficulty drift, and staleness, then proposes retirement or refresh before a question stops discriminating.

Psychometric drift monitoring · retirement recommendations
Agent 04

Blueprint co-pilot

Proposes paper blueprints from historical performance data — balancing difficulty, coverage, and discrimination — so institutions design better tests, not just legal ones.

Historical calibration · institution approves, agent never publishes

Also on the roadmap: adaptive testing that adjusts difficulty per candidate without compromising comparability, and cross-border credential portability so a verified result travels with the candidate instead of living in one institution's database.

teaOS didn't start as a deck. It started as a working system — five contracts deployed to 0G mainnet, a full question pipeline running against live TEE inference, and a Miden bridge written against the raw Rust SDK because no higher-level tooling existed yet.

Most of the hard problems here weren't product decisions, they were engineering ones: a Send-bound bug in the Miden client that had to be root-caused from compiler output, a faucet policy that failed a VM kernel assertion, a silent success bug that would have marked a paper ready with no timelock at all. Each one was found by running the thing, not reading about it.

That's the bet. This is a category where the only credible founder is one who has already gotten the cryptography to actually work.

Where this goes

Integrity shouldn't require trust.

Every year, hundreds of millions of people sit an exam that decides what the rest of their life looks like — and are asked to believe, on faith, that nobody opened the paper early. When that faith breaks, it doesn't just cost a result. It costs a year, a rank, a job, sometimes a career.

teaOS makes that faith unnecessary. Not by promising harder, but by building a system where the promise is enforced by mathematics that answers to no one — and where any candidate, on any phone, can check it for themselves in ten seconds.

We're not asking institutions to be more trustworthy. We're making trustworthiness something they no longer have to be taken at their word for.
