The problem

Every paper leak ends the same way.

An investigation. A committee. A promise it won't happen again. Then the same system gets rebuilt, exactly as it was.

The reason isn't that people running exams are careless. It's structural. In every exam system operating today, some human being holds the question paper before the exam starts — a database administrator, a printing vendor, a regional officer, someone with production access at 2am. Security is a rule asking them not to look.

A rule has no enforcement layer. And when something does go wrong, the audit logs that would prove it sit on servers owned by the same institution being investigated.

Every exam system in the world currently asks candidates to trust an administrator. teaOS removes the administrator from the trust equation — not with policy, with cryptography.

Architecture

Four services, split along trust boundaries.

The system isn't decomposed for scaling convenience. It's decomposed so that the component handling your web session and the component holding decryption keys are different processes, with different privileges, that cannot be collapsed into each other.

Service 01

Application API

Node · Express · PostgreSQL · Redis

Identity, scheduling, blueprints, exam sessions, job orchestration. This is the surface the internet talks to, and it is deliberately the least privileged part of the system.

  • canQueue work, read metadata, write audit records
  • cannotDecrypt a question or a paper
  • cannotReach a paper key, even with database access
Service 02

Crypto workers

Isolated queue consumers · BullMQ

Where encryption actually happens. Pulls jobs off Redis, performs envelope encryption, writes to 0G Storage, signs chain transactions. Holds the question-bank master key.

  • canEncrypt, decrypt, assemble, anchor
  • cannotBe reached directly over HTTP
  • cannotRetain a paper key past assembly
Service 03

Miden bridge

Rust · Axum · miden-client

A separate process, and its separateness is engineering necessity rather than taste. Miden proves transactions client-side and has no first-party Node SDK — so the real Rust client runs here, on a dedicated OS thread with its own single-threaded runtime, reached only over an internal channel.

  • canSeal keys into notes, submit and consume transactions
  • cannotRelease a sealed key before its block height
Service 04

Chain registries

Solidity · 0G Chain

Five append-only contracts — questions, papers, submissions, results, audit log. They store hashes and block numbers. Nothing else.

  • canProve what existed, and when
  • cannotHold content, identity, or scores
  • cannotBe rewritten, including by us

The Miden bridge running on its own thread isn't an aesthetic choice. Miden's client type isn't thread-safe across an async web server — its transaction prover loses its Send bound at an API boundary — so sharing it across request threads is impossible. Isolating it in an actor happens to mirror Miden's own model, where one account processes one state transition at a time.

Cryptographic design

Two keys, with deliberately different lifetimes.

Most systems that claim encryption have one key that opens everything, held somewhere convenient. The interesting design work here is in the second key — the one that exists for a few seconds and then stops being ours.

Key one · long-lived

Question-bank master key

Protects individual questions at rest. Every accepted question is sealed under it with AES-256-GCM, written to 0G Storage, and anchored by content hash.

Assembly runs in a specific order, and the order is the whole point. Workers decrypt the selected questions individually, compose the paper in memory, generate a fresh content key, encrypt the composed paper under it, upload the ciphertext, and anchor its hash. Only then does the key go to the bridge to be sealed — and the moment it does, the worker discards it.

Between assembly and exam start, the paper key exists in exactly one place: inside a Miden note the network refuses to open. Not in our database. Not in a vault we control. Not in a config file. If our entire infrastructure were seized during that window, the paper would still be unreadable.

This is also why a compromised database doesn't leak an exam. The rows contain a storage root, a content hash, a note identifier, and a block height. Every one of those is safe to publish — we anchor them publicly on purpose.

The timelock

How the paper actually stays shut.

A scheduled release in a normal system is a timestamp column and a background job. Anyone with write access can move the date, and nobody outside would know. We needed the release condition to live somewhere no operator could reach.

The paper's content key is wrapped into a Miden P2IDE note carrying two block heights: timelock_height, before which the note cannot be consumed at all, and reclaim_height, after which the original sender can take it back once the exam window has closed. Both are enforced by the note's script executing inside Miden's VM as part of transaction validity — not by a permission check in our code that a privileged user could route around.

Because the condition is a block height rather than a wall-clock time, it also can't be defeated by changing a server's clock. We derive the target height from the exam schedule at sealing time and record the derivation, so the mapping from "9:00am Tuesday" to a specific block is itself auditable.

One detail worth stating plainly, because it's the kind of thing that sounds like a gap: a P2IDE note must carry at least one asset. We issue our own private fungible token for this — it is not a currency, it has no market, and it never leaves our accounts. Its only job is to be the thing whose transfer the timelock governs. The exam key is not stored in that asset, and could not be: Miden stores only a hash of asset data on chain, never the bytes. The wrapped key stays bridge-side and is released only after a real consume transaction against the network succeeds.

Delivery

Every candidate gets a different paper made of identical questions.

Each exam session is issued a randomization seed at enrolment. Question order and the order of options within each question are derived from it deterministically. Same question set, same difficulty profile, same marks — different arrangement.

The property this buys isn't obfuscation. It's that positional information becomes worthless. "Question 4 is C" is true for exactly one candidate and misleading for everyone else. Copying from a neighbouring screen stops being a glance and starts requiring you to read and solve the entire question, which is the activity we were trying to measure anyway.

Because the seed is stored and the derivation is deterministic, we can reconstruct precisely what any individual candidate saw — months later, during a dispute — without ever storing a separate personalized copy of their paper. The seed is a few bytes; the paper regenerates from it.

Answers autosave continuously, encrypted client-side. On submission, a private Miden note commits the submission. Its nullifier makes a second silent submission impossible, while the note itself reveals neither the candidate's identity nor their answers on chain.

Verification

Six independent checks, no login required.

A candidate enters an application number and date of birth on a public page. The system doesn't look up a stored "verified" flag — it re-derives every claim from source and reports each one separately, so a partial failure is visible rather than hidden behind a single green tick.

  • 01Answer hash matches The answers on record hash to the value committed at submission time.
  • 02Submission hash matches The submission commitment matches what was anchored, byte for byte.
  • 03Official result hash matches The published score re-derives to the hash anchored in ResultRegistry.
  • 04Miden note status is consistent The submission note exists, and its nullifier shows exactly one consumption.
  • 050G Storage Merkle proof verifies The stored blob proves membership under the root that was anchored.
  • 06Chain transaction is valid and final The anchoring transaction exists on 0G Chain at the stated block.

None of these checks trusts our database. Each one goes to the original source — the chain, the storage layer, the Miden network — and recomputes. A journalist, a court, or a competing vendor can run the same checks against public infrastructure and get the same answer without our cooperation.

Component choices

What the architecture required, and what met it.

We didn't start from a shortlist of chains. Each requirement below came out of the design, and only then did we go looking for something that satisfied it.

A release condition no operator can override

Everything else in the system is downstream of this. If any human can move the release time, the entire integrity claim collapses. It had to be enforced during transaction validation, not by application logic.

Miden P2IDE notes
timelock enforced in-VM
AI review that never exposes the question

Duplicate detection and difficulty prediction need a capable model. Sending an unreleased question to an ordinary inference API means handing the paper to a vendor and hoping. We needed attestable execution.

0G Compute
Intel TDX enclaves
Storage where tampering is detectable, not just prohibited

Encryption stops reading. It doesn't stop substitution. We needed to prove a retrieved paper is byte-identical to the one anchored, without trusting the storage operator.

0G Storage
content-addressed, Merkle proofs
An audit record outside our own control

Logs owned by the accused prove nothing. And batching once a day makes the trail too coarse to answer "when exactly did this question enter the bank" — so anchoring had to be cheap enough to do per item.

0G Chain
EVM L1, per-item anchoring

Blockchain is doing one specific job here and we'd rather name it precisely than overclaim: it makes a record that exists outside the institution's reach and cannot be edited afterwards — by them, by us, or by anyone who compromises either of us. Nothing about the exam's fairness depends on decentralization as an ideology.

Engineering discipline

The failures we designed against.

Security systems don't usually fail loudly. They fail by reporting success while doing nothing. Three of these were found by running the system, not by reasoning about it — which is the only reason we trust the rest of it.

Failure mode

Silent success

An unimplemented endpoint returned an error message with a success status code. The caller's check passed, the error body was parsed as a valid result, and a paper was marked ready with no timelock attached to it at all.

NowEvery response from the bridge is validated against a strict schema regardless of status code. A well-formed lie fails as loudly as a crash.
Failure mode

The privileged exception

The usual way this system would rot is an emergency override added under pressure — "just for the admin, just this once" — which then becomes the thing an attacker targets.

NowOne code path gates exam start for every role. There is no branch on privilege level, so there is nowhere to add an exception without deleting the check for everyone.
Failure mode

Orphaned key material

The bridge originally provisioned a fresh account on every restart, which would have stranded sealed notes behind an identity the service no longer had.

NowAccounts persist across restarts and are verified present in the local store before reuse, with a fresh pair provisioned only if that check fails.
Failure mode

Retries corrupting state

A queued job that failed partway through an external call would re-enter and hit a state guard written for the first attempt, reporting a confusing conflict instead of genuinely retrying.

NowState machines accept their own in-progress states as valid re-entry points, so a retry is a retry rather than a spurious error.

What comes next

Agents that watch the exam, and can be audited themselves.

Exams generate far more signal than a human team can watch in real time. The moment you automate that watching, you create a new trust problem — who audits the watcher — and most proctoring vendors simply don't answer it.

Our answer is that agents get the same treatment as everyone else in this system. They run inside 0G Compute enclaves, so they never see raw candidate data in the clear. Every judgement they make — every flag, every escalation — is anchored on chain alongside the evidence that triggered it. An agent's decisions become exactly as reviewable as a human invigilator's, except they don't get tired at hour four, and unlike a human they can be re-examined years later.

Agent 01

Live invigilation

Watches session telemetry across every centre simultaneously — focus loss, timing irregularities, input patterns — and produces a signed evidence bundle instead of an unexplained accusation.

Runs in TEE · decisions anchored · human review required before action
Agent 02

Collusion detection

Statistical analysis across centres and cohorts to surface coordinated answer patterns that are invisible when each session is examined alone.

Cross-centre correlation · privacy-preserving aggregates
Agent 03

Question bank health

Continuously audits the bank for over-exposure, difficulty drift, and staleness, then proposes retirement or refresh before a question stops discriminating between candidates.

Psychometric drift monitoring · retirement recommendations
Agent 04

Blueprint co-pilot

Proposes paper blueprints from historical performance data — balancing difficulty, coverage, and discrimination — so institutions design better tests, not just compliant ones.

Historical calibration · institution approves, agent never publishes

Also on the roadmap: adaptive testing that adjusts difficulty per candidate without compromising comparability of scores, and cross-border credential portability so a verified result travels with the candidate instead of living in one institution's database.

Where this goes

Integrity shouldn't require trust.

Every year, hundreds of millions of people sit an exam that decides what the rest of their life looks like — and are asked to believe, on faith, that nobody opened the paper early. When that faith breaks, it doesn't just cost a result. It costs a year, a rank, a job, sometimes a career.

teaOS makes that faith unnecessary. Not by promising harder, but by building a system where the promise is enforced by mathematics that answers to no one — and where any candidate, on any phone, can check it for themselves in ten seconds.

We're not asking institutions to be more trustworthy. We're making trustworthiness something they no longer have to be taken at their word for.
